每个人同时维护自己的模块文档和测试。D 只整合大家提供的材料；B 提供真实性能数据，C 提供真实事务记录，A 提供真实存储和缓冲记录。

C 的后期工作较多：事务安排在执行器和索引稳定之后，A 协作处理存储恢复接口，D 协作处理会话归属；如时间不足，优先协商调整范围，不省略索引正确性测试。

| S4 / M4 | C，A/B 配合 | 无优化 SQL 执行与数据修改 | 建表 -> 插入 -> 查询 -> 排序 -> 修改 -> 删除 -> 重开完整链路通过 | 待开发，依赖 S2/S3 |

| S6 / M6 | D | 鉴权、审计、Web、计划树 | API 权限测试与真实浏览器演示通过，错误不显示旧结果冒充成功 | 待开发；API 设计可提前 |

顺序描述的是依赖和验收，不要求所有人轮流等待。B 可以先做纯解析测试，C 可以先测试独立算子和内存 B+ 树，D 可以先定 API 和界面数据格式。集成时只使用已完成模块的真实结果。

## 4. 协作规则

1. 使用同一个新项目目录，不各写一套不兼容的数据格式。旧版仅作行为参考，新项目不 import 旧版实现。
2. 每次提交集中于一个模块或一个接口变更。建议分支如 `codex/m2-buffer`、`codex/m3-sql`，完成测试和复核后再合入 `main`。
3. 修改共享模型、页格式或 PlanNode 前，先更新接口说明并让调用方复核；记录兼容性和数据迁移方式。
4. 合并前提供可复现命令和结果。计划中的测试标记“待运行”，不能写成“通过”。
5. 每个模块结束做一次短讲：需求、输入输出、核心算法、失败场景、测试证据、当前限制。
